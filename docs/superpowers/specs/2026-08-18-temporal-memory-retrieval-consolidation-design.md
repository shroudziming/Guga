# 时间记忆检索与异步巩固设计

## 1. 背景与目标

当前记忆系统已经具有普通语义检索、Agent Tool Calling 和分阶段记忆巩固能力，但时间语义的解析、检索和巩固尚未形成统一的数据流。本设计将时间能力拆成两条相互独立的线路：

1. 同步记忆检索：模型在现有 Agent Loop 中识别并解析时间，通过标准工具调用检索时间相关记忆。
2. 异步记忆巩固：按固定对话轮次或正常退出触发，结合多轮对话、消息时间和已解析的语义时间生成或修改长期记忆。

普通语义检索与时间检索是两路独立证据，不要求同时满足语义相似和时间重叠：

$$
C_{final} = C_{semantic} \cup C_{temporal}
$$

本阶段不处理跨层重复记忆，也不为旧记忆格式增加运行时兼容逻辑。新流程稳定后，再单独迁移旧数据。

## 2. 总体架构

采用标准 Tool Calling 方案，将 `memory_time_search` 注册为与其他工具同级的工具：

```text
用户消息
  → 普通语义检索
  → 组织历史、语义上下文、当前时间和工具定义
  → 模型响应
       ├─ 包含任意 tool_calls
       │    → 执行全部工具
       │    → 将工具结果加入上下文
       │    → 继续 Agent Loop
       └─ 不包含 tool_calls
            → 输出最终回复
            → 保存完整 turn
```

时间意图只决定模型是否调用 `memory_time_search`，不决定 Agent Loop 是否结束。没有时间意图时，模型仍可调用文件、命令或其他工具；存在时间意图时，也可在同一响应中调用多个不同工具。

Agent Loop 的终止条件保持为模型不再返回任何工具调用，或达到现有最大工具轮数。

## 3. 时间工具协议

### 3.1 模型上下文

第一次及后续模型调用均可获得明确的参考时间与时区，例如：

```text
当前时间：2026-08-18T10:30:00+08:00
时区：Asia/Hong_Kong
```

模型负责结合参考时间、对话上下文和相关历史时间，将自然语言时间转换为绝对区间。检索器不再自行理解“明天”“下个月”等自然语言表达。

如果模型无法可靠确定“那天”等指代所对应的绝对时间，应向用户澄清，不得猜测。

### 3.2 工具参数

`memory_time_search` 接收一个或多个时间查询：

```json
{
  "time_queries": [
    {
      "original_expression": "8月20号",
      "start_at": "2026-08-20T00:00:00+08:00",
      "end_at": "2026-08-21T00:00:00+08:00",
      "relation": "overlap",
      "granularity": "day",
      "time_basis": "semantic"
    }
  ]
}
```

协议约束如下：

- 时间使用带时区的 ISO 8601 格式。
- 时间区间采用左闭右开语义 $[start\_at, end\_at)$。
- 一天解析为当天零点到第二天零点。
- 一句话包含多个时间时，生成多个 `time_queries`。
- `original_expression` 保留用户原始表达，供调试和异步巩固追溯。
- `time_basis` 取 `semantic` 或 `transaction`；默认检索事件语义时间，只有“昨天聊了什么”等明确查询对话发生时间的请求才使用 `transaction`。
- “最近一周”和“本次会话期间”等表达先转换为绝对区间，再执行匹配。
- 工具参数就是时间解析的结构化结果，不从助手文本中使用正则二次提取。

### 3.3 参数校验

执行工具前必须检查：

- `time_queries` 非空。
- `start_at` 和 `end_at` 均包含有效时区。
- `start_at < end_at`。
- `relation` 和 `granularity` 属于允许值。
- 多个查询分别校验，并能定位具体的错误下标。

校验失败时返回结构化工具错误，让模型在 Agent Loop 内修正。只有校验成功并实际执行的查询才写入本轮 `temporal_context`。

## 4. 时间匹配与排序

### 4.1 各类时间字段

- `semantic_event.start_at/end_at`：事件实际发生区间。
- `archival_memory.valid_at/invalid_at`：事实成立的有效区间。
- `event_summary.time_window_start/time_window_end`：总结覆盖的事件区间。
- `turn.temporal_context.time_queries`：该轮对话解析出的语义时间区间。

这些字段均可参与时间检索，但工具结果必须保留 `record_type` 和原始字段，不能混淆事件发生时间与事实有效期。

`created_at` 只表示消息或记录的创建时间，不能代替语义时间。只有 `time_basis=transaction`，即查询“昨天的对话”“最近聊过什么”等对话时间时，才允许使用消息 `created_at`。

### 4.2 区间关系

对于 `overlap`，候选区间与查询区间的匹配条件为：

$$
memory_{start} < query_{end}
\quad \land \quad
memory_{end} > query_{start}
$$

此外支持：

- `before`：候选结束时间不晚于查询边界。
- `after`：候选开始时间不早于查询边界。
- `recent`、会话范围等语义：解析为绝对区间后使用 `overlap`。

新写入的可检索记录必须满足新时间协议。缺失或非法时间字段的数据不进入新时间检索。旧数据在功能构建完成后通过独立迁移流程调整，不在检索代码中维护兼容分支。

### 4.3 生命周期

事件的 `active`、`cancelled`、`replaced` 等状态独立于发生区间。已取消事件仍可按原发生时间召回，但结果必须携带生命周期状态，避免模型将已取消安排表述为仍然有效。

同理，`archival_memory.invalid_at` 表示事实何时不再成立，不表示删除记录。

### 4.4 BGE-M3 排序

时间检索分成两步：

```text
结构化时间字段筛选候选
→ 使用 BGE-M3 计算用户问题与候选文本的语义相似度
→ 在时间候选内部排序
```

语义分数只用于时间候选内部排序，不是进入时间候选集的必要条件。建议排序顺序为：

```text
语义相似度降序
→ 时间信息完整度
→ 生命周期可信度
→ 更新时间降序
```

多个时间查询的结果分别分组，并作为独立的 `[Time Context]` 工具结果返回 Agent Loop。BGE-M3 排序失败时仍返回时间匹配候选，降级为确定性的时间顺序并记录日志。

## 5. Session Turn 数据

时间解析结果属于一次完整用户交互，而不是仅属于最终助手消息：

```json
{
  "turn_id": "turn_001",
  "user_message": {
    "id": "msg_user_001",
    "content": "8月20号有什么事情",
    "created_at": "2026-08-18T10:30:00+08:00"
  },
  "temporal_context": {
    "source_message_id": "msg_user_001",
    "reference_time": "2026-08-18T10:30:00+08:00",
    "time_queries": []
  },
  "tool_interactions": [],
  "assistant_message": {
    "id": "msg_assistant_001",
    "content": "..."
  }
}
```

一个 turn 从用户发送消息开始，到 Agent Loop 产生最终回复结束。模型内部调用多少次都只计算一个 turn。

- `temporal_context` 从成功执行的时间工具参数生成。
- 同一 Agent Loop 多次调用时间工具时，将查询汇总到同一个 turn。
- 没有调用时间工具时，不写入 `temporal_context`。
- `tool_interactions` 保存工具名、参数、结果记录 ID 和状态，供调试与巩固使用。
- 这些元数据不会拼进用户可见的消息文本，也不直接等同于长期记忆。

## 6. 异步两阶段巩固

### 6.1 触发机制

巩固采用固定轮次触发与正常退出触发：

```text
每个完整 turn 保存后
  → 未巩固 turn 数达到 consolidation_interval_turns
       → 提交异步巩固任务

正常退出
  → 等待正在运行的巩固任务
  → 巩固所有剩余 turn
  → 关闭程序
```

固定轮次阈值使用现有配置体系，不硬编码。正常退出包括程序支持的 `exit`、`quit`、EOF 和可捕获的正常关闭路径。强制结束或断电无法执行退出巩固，但未巩固水位必须保留，以便下次启动恢复。

### 6.2 输入与证据

每批巩固读取：

- 尚未巩固的多轮用户及助手消息。
- 每条消息的事务时间 `created_at`。
- 每轮的 `temporal_context` 和工具交互记录。
- 相关现有语义事件、事件总结、归档记忆和用户画像。

用户消息是事实和意图的主要来源。助手回复只用于理解对话流程，不能单独作为新增用户事实的依据。工具结果用于关联已有记忆。

时间冲突的证据优先级为：

```text
用户后续明确修正
> 用户明确给出的绝对时间
> 当前轮 temporal_context
> 已有记忆时间
> 巩固模型自行推断
```

`temporal_context` 是高优先级证据，但不是不可修改的最终事实。模型不得仅凭常识覆盖用户明确给出的时间。

### 6.3 第一阶段：事实层

第一阶段生成经过校验的 `semantic_event` 操作和 `event_summary`：

- 事件操作支持 `create`、`update`、`cancel`、`replace`。
- `created_at` 和 `updated_at` 由程序写入，模型不能覆盖。
- 事件总结基于本批次确认后的事件生成，并保存 `source_event_ids` 与 `evidence_turn_ids`。
- 写入前校验时间格式、时区、区间顺序、状态值和引用完整性。
- 校验失败的操作不写入，并记录 debug 信息。

### 6.4 第二阶段：高层记忆

第二阶段只读取已经校验并提交的事实层结果，再更新：

- `archival_memory`，使用 `valid_at/invalid_at` 表达事实有效期。
- `user_model`，只保存相对稳定且跨对话有价值的信息。

一次具体安排通常属于语义事件或归档记忆，不应直接写成稳定用户画像。

### 6.5 巩固水位

每批任务记录：

```text
consolidation_batch_id
processed_turn_ids
trigger_reason: interval | exit
started_at
completed_at
status
debug/error
```

同时维护已完成 turn、已巩固 turn、待处理数量和运行中批次。固定轮次任务只消费未巩固 turn，退出任务只补齐尾批，失败任务可以恢复或重试。

## 7. 错误处理与日志

时间工具的关键行为如下：

- 没有匹配结果是成功的空结果，不是异常。
- 存储读取失败返回工具错误，不能伪装成“没有相关记忆”。
- 非法时间参数返回可定位的结构化错误，由模型在工具轮数限制内修正。
- BGE-M3 失败时保留时间候选并降级排序。
- 达到最大工具轮数时沿用现有 Agent Loop 的终止策略。

每次时间工具调用记录：

```text
turn_id
tool_call_id
reference_time
time_queries
candidate_count
returned_memory_ids
ranking_model
duration_ms
status/error
```

巩固日志记录触发原因、消费的 turn、两阶段输出、校验结果、实际写入的记忆 ID 和巩固水位变化。

## 8. 验收标准

1. 无时间意图时不调用时间工具，但仍可调用其他工具并正常继续 Agent Loop。
2. “8 月 20 号”按当前年份和时区解析为当天的左闭右开区间。
3. 多个时间表达生成多个查询，结果按查询分组。
4. 相对时间根据当前参考时间和上下文解析为绝对区间。
5. 无法确定的时间指代触发用户澄清，不进行猜测检索。
6. 普通语义检索与时间检索互不求交，时间相关但语义分数低的记录仍进入 `[Time Context]`。
7. 已取消事件可按发生时间召回，并携带 `cancelled` 状态。
8. 未达到固定轮次阈值时不触发巩固；达到阈值时仅处理未巩固 turn。
9. 正常退出前等待运行任务，并完成剩余 turn 的尾批巩固。
10. 异常中断后可根据持久化水位恢复未完成巩固。
11. 在 2026 年 8 月 18 日输入“我 8 月 20 号有个面试”，正常退出触发巩固；重启后询问“8 月 20 号有什么事情”，时间工具能够召回新生成的语义事件并生成正确回答。

端到端验收同时检查 session、四类记忆文件和 debug 日志。旧记忆迁移和跨层重复治理不在本阶段范围内。
