# LangGraph Agent Task Runtime Design

## 目标

为 Guga 增加可验证的智能体任务执行流程，使其能够先生成并展示计划，在用户批准后持续调用现有工具，直至任务完成、需要修订计划或连续三次执行仍不符合预期。执行过程需要独立留痕，任务终态需要以摘要和 trace 引用接入长期记忆。

## 范围

第一版包括：

- 使用 LangGraph 编排计划、批准、执行、验证、重试和终态。
- 计划获得一次批准后，计划范围内的工具调用不再逐个批准。
- 计划发生实质变化时，重新展示修订计划并等待批准。
- 每个步骤最多执行三次；第三次仍不符合预期时任务失败。
- 缺少继续执行所必需的输入、工具或外部条件时，任务进入阻塞状态。
- 保存开发者可直接读取的工具调用 trace。
- 长期记忆保存任务终态摘要以及对应 trace 的稳定引用。
- 通过显式 `/task` 命令进入智能体任务流程，普通聊天继续使用现有入口。

第一版不包括：

- 工具风险分级或读写行为分类。
- 每次工具调用单独批准。
- 完整 stdout、stderr 或文件内容 artifact 归档。
- 让 Guga 在普通对话中主动读取原始执行 trace。
- 多智能体协作。
- 任务摘要加入 RAG 的具体排序和召回策略。

## 核心原则

LLM 负责理解目标、生成计划、选择行动、解释工具结果和生成最终报告。运行时负责批准门、工具范围、状态转换、三次重试上限和终态约束。任何不能依赖模型自觉遵守的规则都由代码强制执行。

普通聊天与智能体任务使用相同的模型、人格、工具注册表和记忆管理器，但使用不同的编排路径。智能体流程不复用 `ChatSession` 当前的自动工具循环，以免绕过计划批准。

## 状态机

任务状态为：

```text
planning
  -> awaiting_approval
      -> executing
          -> completed
          -> blocked
          -> failed
          -> planning (revised plan)
               -> awaiting_approval
```

初始计划和每次修订计划都包含：

- 任务目标。
- 有序步骤。
- 每一步的可观察预期结果。
- 每一步允许使用的工具集合。
- 整体完成条件。

用户批准的是当前 `plan_revision`。只有 `approved_revision == plan_revision` 时，图才能进入执行节点。

## 执行和验证

每个步骤遵循以下循环：

1. 模型基于已批准计划、当前步骤和已有证据选择一个工具调用。
2. 运行时确认工具名称属于当前步骤的 `allowed_tools`。
3. 运行时执行工具并保存调用参数与返回结果。
4. 模型比较实际结果与 `expected_result`，返回结构化验证结论。
5. 运行时根据验证结论决定进入下一步、重试、修订计划或失败。

`attempt` 在每次实际工具调用后增加。步骤验证通过后清零。验证不通过且无需修订计划时，只要 `attempt < 3` 就继续当前步骤；第三次仍不通过时进入 `failed`。

模型不能自行提高重试次数，不能绕过计划批准，也不能仅凭自然语言声明任务完成。只有所有步骤验证通过，运行时才允许进入 `completed`。

## LangGraph 边界

新增 `guga.agent` 包承担编排：

- `state.py` 定义计划、行动、验证和任务状态。
- `model_adapter.py` 将现有 `ChatModel` 适配为结构化规划、行动选择、验证和最终报告接口。
- `trace.py` 追加保存执行事件。
- `graph.py` 定义 LangGraph 节点、条件边和强制约束。
- `runner.py` 隐藏 `thread_id`、`Command(resume=...)` 和 checkpointer 细节。
- `outcome.py` 定义提交给长期记忆的终态对象。

现有 `ToolRegistry.execute()` 继续作为唯一工具执行入口。现有 `OpenAICompatibleChatModel` 的结构化回复和工具 schema 能力继续复用，不引入 LangChain `create_agent`。

第一版可以使用内存 checkpointer 完成单进程流程；如果需要进程退出后恢复待批准任务，则使用 SQLite checkpointer。具体依赖版本在实现时通过官方兼容范围固定。

## 批准交互

CLI 使用显式命令区分普通聊天和智能体任务：

```text
/task <任务描述>
/approve
/reject
```

`/task` 只生成计划并返回 LangGraph interrupt，不执行任务工具。`/approve` 使用同一 `thread_id` 恢复图。`/reject` 将任务结束为阻塞状态，不执行工具。

如果执行中需要修订计划，图再次 interrupt，CLI 展示新版本并等待新的 `/approve` 或 `/reject`。

## 执行 Trace

每个任务保存独立的追加式 JSONL：

```text
data/agent_runs/<agent_id>/<task_id>/trace.jsonl
```

第一版至少记录：

- 任务创建和计划版本。
- 计划批准或拒绝。
- 当前步骤和尝试次数。
- 模型提出的工具名称与参数。
- 工具返回给运行时的实际结果。
- 验证结论及下一状态。
- 最终完成、失败或阻塞事件。

trace 面向开发者和 Codex 调试，不自动注入普通聊天上下文，也不提供给 Guga 作为新的读取工具。

当前工具会截断部分返回内容，因此第一版 trace 能还原运行时实际看到的过程，但不能保证还原工具产生的全部原始输出。完整输出 artifact、预览和截断元数据作为后续专项设计。

## 长期记忆对齐

任务到达 `completed`、`failed` 或 `blocked` 后生成一个 `TaskOutcome`：

```text
task_id
goal
status
summary
tools_used
trace_ref
completed_at
```

`TaskOutcome` 写入：

```text
data/memory/agents/<agent_id>/task_outcomes.jsonl
```

它不写入现有 `semantic_events.jsonl`，因为现有语义事件表达用户事实，并强制 `subject == "user"`。任务结果属于智能体执行历史，不应污染用户画像。

同一 `task_id` 的终态只允许写入一次，避免图恢复或节点重放造成重复记忆。第一版保存任务摘要和 trace 引用，但暂不设计其 RAG 召回权重。

## 普通聊天边界

现有 `ChatSession` 会在模型提出工具调用后立即执行。为保证智能体任务不能绕过批准，CLI 中的普通聊天会话不应获得文件、目录和命令执行工具；这些操作工具只交给 `AgentTaskRunner`。

时间解析是否继续作为普通聊天内部工具，需要在实现时通过独立 registry 或显式工具列表保留，不能用风险分级替代边界设计。

## 错误处理

- 非法计划、非法结构化输出和未知工具不执行，返回模型修复；若需要改变计划则重新批准。
- 工具抛出异常时，`ToolRegistry.execute()` 的结构化错误作为一次实际结果参与验证和重试。
- 三次实际执行仍不符合预期时进入 `failed`。
- 缺少必要输入、工具能力或外部条件时进入 `blocked`，不进行没有意义的三次重试。
- trace 写入失败时不得继续执行无法审计的工具调用；任务进入阻塞或失败状态并向用户说明。
- 终态记忆写入通过 `task_id` 幂等；写入失败不得把已经完成的外部动作重新执行。

## 测试策略

单元测试使用伪模型和伪工具，不调用真实 API 或真实 shell。必须覆盖：

- 未批准时工具调用次数为零。
- 批准后连续执行到完成。
- 验证不匹配时最多执行三次。
- 第三次失败后进入 `failed`。
- 修改计划后重新等待批准。
- 计划范围外工具不执行。
- trace 包含调用、结果、重试和验证事件。
- 原始 trace 不进入聊天历史或用户语义事件。
- 每个终态任务只写入一个 `TaskOutcome`。
- `TaskOutcome.trace_ref` 能定位任务 trace。

CLI 测试验证 `/task`、`/approve` 和 `/reject` 路由。现有聊天、工具调用、记忆和人格测试必须继续通过。

## 已知限制与后续工作

- 当前工具输出长度限制可能影响完成判定、故障复盘和原始现场还原。后续需要单独设计完整输出归档、模型可见预览、截断元数据和证据引用。
- 第一版任务摘要只持久化，不定义其 RAG 排序和召回策略。
- 第一版不做工具级风险分类或逐调用审批。
- 如果只使用内存 checkpointer，程序退出后无法恢复等待批准的任务。
