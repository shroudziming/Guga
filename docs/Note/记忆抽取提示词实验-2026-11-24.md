# 记忆抽取提示词与 Schema 实验（2026-11-24）

## 目标

修正 Stage 1 记忆抽取提示词中容易被小模型误读的伪 Schema，并在不下载新模型的前提下，先用现有 0.5B 模型验证链路、比较 DeepSeek 教师输出。正式训练与训练前后评估的目标模型是 `Qwen2.5-1.5B-Instruct`；本次 0.5B 结果只作为提示词压力测试，不作为目标模型基线。

固定输入：

```text
created_at: 2026-11-24T10:00:00+08:00
user_message_id: msg_user_benchmark
user_text: 我明天下午三点要参加一家公司的产品经理面试。
```

本地推理固定为 greedy decoding；速度测试每次最多生成 256 token，完整输出最多生成 768 token。

## 开发环境核对

- 实际存在两个不同的本地检查点：
  - Hugging Face 缓存中的 `Qwen2-0.5B` 是基座模型。
  - Guga `models_cache` 中的 `Qwen2.5-0.5B-Instruct` 是 dsh 流程使用的指令模型。
- 最终实验使用 `D:\work\LLM\Guga\models_cache\Qwen2.5-0.5B-Instruct`。
- 本机尚未发现完整的 `Qwen2.5-1.5B-Instruct` 检查点，因此本轮没有运行目标模型，也没有触发下载。
- Benchmark 强制 `local_files_only=True`，没有下载模型或依赖。

## 改动记录

### v2：明确字段语义并加入合法示例

- 把 `"create|update|replace|cancel|ignore"` 改成明确的合法单值列表，禁止复制带 `|` 的字符串。
- 定义 `event_kind` 为事件类别，定义 `entity` 为现实对象、组织、活动或主题。
- 要求 `time_expression` 逐字来自 `user_text`。
- 要求 `source_message_ids` 引用直接支持事件的输入消息 ID。
- 加入完整合法 JSON 示例。

结果：

- `Qwen2-0.5B` 基座模型反复续写 Reflection Contract，768 token 用尽仍没有 JSON。
- `Qwen2.5-0.5B-Instruct` 只输出根级 `appraisal/felt_response`。
- 发现 Validator 会用 `setdefault` 补空数组，从而把根级反思错误地判为合法。

### v3：收紧顶层格式与反思嵌套

- 顶层必须且只能包含 `semantic_event_operations` 和 `event_summaries` 两个数组。
- `guga_reflection` 只允许嵌套在单个事件操作中。
- 示例按 `include_guga_reflection` 动态生成。
- Validator 只检查这一可确定的结构约束，不尝试用字符串匹配判断事件语义。

结果：Validator 正确拒绝根级反思，但 0.5B Instruct 仍然只输出根级反思。

### v4：调整指令顺序

- 把完整 Persona Skill 放到宿主 Schema 之前。
- 把宿主格式约束、字段规则和完整示例放在更靠近输入的位置。

结果：0.5B Instruct 首次生成完整、可解析且通过结构 Validator 的事件 JSON。

结构通过不等于语义正确。这里仍有三个语义错误：

3. `create` 多输出了 `target_event_id`；当前规范化会移除它，所以不造成持久化污染，但说明模型尚未掌握规则。

## 目标模型与后续评估口径

- 目标模型固定为 `Qwen2.5-1.5B-Instruct`，后续训练前基线、LoRA 训练和训练后评估必须使用同一个 1.5B 基座与同一冻结测试集。
- v4 在这条 0.5B 样本上解决了枚举照抄、角色误填、消息 ID 漏引和 JSON 结构问题，但不能据此断言 1.5B 是否已经具备这些能力。
- 0.5B 暴露出的证据忠实度与时间归一化问题可以进入 1.5B 基线测试集；只有 1.5B 基线仍然失败的部分才应成为 LoRA 数据重点。
- 单条样本只能验证链路，不能估算稳定失败率。正式评估至少应分开统计：
  - `format_failure_rate`：无法解析或不符合顶层/字段结构。
  - `semantic_failure_rate`：证据抄错、时间换算错、事件类别或实体错误。
  - `stage1_rejection_rate`：Stage 1 未通过 Validator 的批次比例。
  - `stage2_commit_failure_rate`：Stage 1 已通过但事务提交失败的批次比例。
  - `two_stage_total_failure_rate`：任一阶段失败的批次比例。
- 本次直接调用抽取器，没有执行持久化事务，因此 `stage2_commit_failure_rate` 记为 N/A；训练前后正式对比必须通过 `MemoryManager` 两阶段提交流程运行同一冻结测试集。

建议在 1.5B 检查点就绪后按以下顺序重跑：

1. 先运行 100 至 200 条冻结开发集，得到未经微调的格式、语义、时间和两阶段提交基线。
2. 将错误按枚举/结构、证据忠实度、相对时间、更新/取消冲突、反思嵌套分类。
3. 只针对 1.5B 的真实失败补训练数据，避免用 0.5B 特有错误污染训练集设计。
4. LoRA 后在同一冻结测试集上比较质量，并单独测量 TTFT、token/s、峰值显存和完整两阶段失败率。
